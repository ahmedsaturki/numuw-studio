# NUMUW Go-To-Market & Delivery System

## Commercial model

NUMUW uses a hybrid model:

- productized entry points for predictable buying and delivery
- scoped projects for complex needs
- recurring Growth Partner work for ongoing optimization

The public site should make the path obvious without forcing every prospect into a custom sales process.

## Offer ladder

| Stage | Offer | Job |
|---|---|---|
| Self-service | Tools / Solution Finder | reduce uncertainty |
| Paid/serious discovery | Diagnostic | establish baseline and priority |
| Focused build | Sprint offers | solve one bounded constraint |
| Connected build | Growth System | connect multiple proven needs |
| Continuous | Growth Partner | operate, measure and improve |

## Qualification

A prospect is worth progressing when there is:
- a real business problem
- a plausible owner/decision-maker
- enough information to establish a baseline
- a meaningful consequence of doing nothing
- a realistic path to delivery
- commercial fit

Red flags:
- outcome guarantee demands without baseline
- unclear ownership
- no decision authority
- unlimited scope for fixed budget
- sensitive data requested through unsafe channels
- refusal to agree on acceptance

## Proposal contract

A proposal should state:
- current state
- objective
- diagnosis/rationale
- scope
- exclusions
- dependencies/client responsibilities
- timeline/milestones
- investment/payment terms
- change control
- acceptance criteria
- ownership/licensing
- support window
- validity date

## Delivery contract

Kickoff:
- confirm scope
- confirm owners
- confirm assets/accounts
- confirm dependencies
- establish baseline where needed
- confirm acceptance method

Build:
- implement bounded work
- test against acceptance criteria
- document meaningful decisions

Handover:
- deliver assets
- verify ownership
- transfer/rotate access securely
- remove temporary access
- provide operating notes/training
- record acceptance

## Proof system

Until real cases accumulate, NUMUW should use:
- clear scope
- transparent limitations
- real artifacts
- measurable internal experiments when they are genuinely real
- founder accountability

Once real client cases exist, use a standard case format:

Problem → Baseline → Intervention → Time window → Evidence → Outcome → Lessons.

Every quantitative claim needs source, scope and context.

## Content system

Content should be organized around:
- buyer problems
- use cases
- decision questions
- industry-specific constraints
- implementation playbooks
- evidence

Do not create pages merely because a keyword exists.

## Conversion system

Every page needs one primary route:
- Contact / diagnostic
- Product
- Tool
- Proof

Secondary actions should support the primary route, not compete with it.

Tools must end with a meaningful next step. Product pages must make fit and non-fit explicit. Proof pages must show evidence rather than generic trust language.

## Measurement

Use:
page_view → tool_start → tool_complete → cta_intent → qualified_conversation → scoped_proposal → won_work

Only the first four can originate from the public browser layer.

Never infer revenue or lead quality from a click alone.

## Operational security

- client-owned accounts whenever possible
- least-privilege access
- no passwords/API keys in chat/project documents
- secure transfer for credentials
- temporary access removed/rotated after use
- external vendors reviewed for privacy/performance impact

## Success definition

NUMUW succeeds when the business can explain:
what it sells, who it is for, why it is credible, what happens after contact, how delivery is controlled, what the client owns, and how improvement is measured.
